# تجربة السايكل كاملة — Saja

## التشغيل وبيانات الدخول

قاعدة التجربة المحلية: **OrangeTenderingSystem** على SQL Server `localhost` باستخدام Windows Authentication.
هذه قاعدة المشروع الأصلية؛ أُضيفت بيانات التجربة إليها دون حذف الحسابات السابقة. الحسابات لا تنتقل تلقائيًا إلى قواعد أجهزة الفريق.
كل حسابات وبيانات هذه القاعدة تجريبية. لم نغيّر منطق النظام أو نتجاوز صلاحياته لتشغيلها.

من مجلد الـrepository الخارجي، في PowerShell أو Git Bash:

```sh
dotnet run --project Orange-Tendering-System --launch-profile https
```

افتحي `https://localhost:7182/Identity/Account/Login`.
في Visual Studio اختاري **https** من قائمة التشغيل بجانب زر Start. أُزيل إعداد التشغيل المنفصل.
أوقفي النسخة السابقة من المشروع إذا كانت تستخدم نفس البورت.

ملف الحسابات وكلمة المرور المشتركة الأولية:
`Orange-Tendering-System/App_Data/SajaDemo/accounts.md`.
الملف محلي ومُستثنى من Git؛ لا ترفعيه مع المشروع. كلمة المرور مولّدة وتظل نفسها عند إعادة تشغيل الأداة.
كل الحسابات جاهزة بالبريد المؤكد ما عدا `supplier-unverified`؛ وحساب `employee-first-login` وحده يطلب تغيير كلمة المرور أولًا.
هذه الحسابات تتجاوز خطوات التسجيل الأولية كبيانات اختبار فقط؛ لتجربة OTP والتسجيل أنشئي موردًا جديدًا من صفحة Register.

لإعادة تجهيز نفس القاعدة عند عضو آخر (PowerShell من مجلد الـrepository):

```powershell
./scripts/Prepare-SajaDemo.ps1
```

التشغيل المتكرر يحافظ على الحسابات والبيانات وتقدّمك؛ لا يحذفها أو يعيد ضبطها. ترفض الأداة تعارض أسماء حسابات التجربة؛ وتعيد استخدام الـOfficer الحالي دون تغيير كلمة مروره.

## الحسابات الرئيسية

كل العناوين التالية تنتهي بـ`@saja-demo.test` ما عدا حساب الـOfficer المذكور ببريده الكامل؛ كلمة مرور الحسابات الجديدة في الملف المحلي المذكور أعلاه.

| بداية البريد | الدور / التجربة |
|---|---|
| admin | Admin؛ المستخدمون والأدوار واعتماد الموردين والوثائق والسجل |
| requester-it | Requesting Department — IT؛ ابدئي طلبًا جديدًا بهذا الحساب |
| requester-facilities | قسم مختلف؛ لا يجب أن يرى طلبات IT الخاصة بمستخدم آخر |
| saja.officer.local@example.com (البريد كامل) | حساب Officer الموجود أصلًا؛ استخدمي كلمة مروره الأصلية، لا كلمة مرور التجربة |
| manager | Sourcing Manager؛ كذلك مقعد المدير في لجنة تقييم العطاءات الستة |
| evaluator-department | ممثل قسم IT في لجنة التقييم |
| evaluator-financial | الممثل المالي |
| evaluator-technical | الممثل الفني |
| evaluator-unassigned | يملك دور اللجنة ولكنه غير معيّن على العطاء؛ يجب منع تقييمه |
| top1، top2، top3، top4 | أعضاء Top Committee؛ يعيّنهم المسؤول في مرحلة الإحالة المناسبة |
| employee-first-login | تجربة تغيير كلمة المرور عند أول دخول |
| employee-inactive | تجربة منع الحساب غير الفعّال |
| supplier-it1 إلى supplier-it4 | أربعة موردين IT معتمدين وفعّالين؛ مناسبون للمنافسة على نفس العطاء |
| supplier-category2 إلى supplier-category11 | مورد معتمد في كل واحدة من الكاتيغوريز العشر الأخرى؛ اسم الفئة في ملف الحسابات |
| supplier-pending | بريد مؤكد وPending؛ دخول صفحة انتظار الاعتماد ومراجعة Admin |
| supplier-unverified | Pending وبريد غير مؤكد؛ الدخول المعتاد مرفوض |
| supplier-rejected | مورد مرفوض؛ دخول مرفوض |
| supplier-suspended | مورد موقوف؛ دخول مرفوض |
| supplier-inactive | الشركة Approved لكن الحساب غير فعّال؛ يجب منع دخوله واختياره وفق فحص الأهلية |

استخدمي Logout بين الأدوار أو browser profiles منفصلة. تبويبان في نفس جلسة المتصفح يشتركان عادةً في تسجيل الدخول.

## العطاءات الجاهزة والقفز لنقطة اختبار

كل الأسماء تبدأ بـ`SAJA DEMO -`. الأوزان الجاهزة 50/50 أمثلة بيانات اختبار وليست قاعدة جديدة أو وزنًا مفروضًا على العطاءات الجديدة.

| العطاء | الحالة الجاهزة | ما تجربينه |
|---|---|---|
| 01 Start here - requirements and weights | Draft، أعضاء اللجنة معيّنون، دون أوزان | طلب الأوزان، أربعة مقترحات، اعتماد المدير ثم فتح التقديم |
| 02 Invitations and editable drafts | Open لـ30 يومًا؛ it1 عنده Draft، it2 Accepted دون عرض، it3 Pending، it4 Declined | حفظ وتعديل ورفع مرفقات وإرسال، قبول ورفض، قبول الدعوة مستقل عن تقديم العرض |
| 03 Two offers - minimum count | Closed، عرضان مرسلان | شرط العدد، إعادة الطرح أو طلب استثناء المدير؛ راجعي العدد والمتطلبات قبل محاولة الانتقال |
| 04 Three offers - ready for compliance | Closed، ثلاثة عروض NotChecked | تسجيل المطابقة لكل عرض ثم Proceed وباقي السايكل |
| 05 Four offers - all compliance states | Closed، أربعة عروض بحالات المطابقة الأربع | Compliant وNonCompliant وPendingClarification وNotChecked، مع أسباب ونواقص؛ ثلاثة threads بحالات Open وAnswered وClosed |
| 06 Expired deadline - submission blocked | Open تاريخيًا لكن الموعد مضى، Draft لـit1 | رفض التعديل أو الإرسال المتأخر والرد على دعوة منتهية؛ قد تعرض الواجهة Pending لأن enum الدعوات لا يحتوي Expired |

وتوجد طلبات شراء مستقلة بحالات Draft وSubmitted وReturned وRejected وAccepted.
الحالات الجاهزة fixtures مباشرة لتسهيل الاختبار؛ ليست دليلًا أن المستخدمين نفّذوا الموافقات فعليًا.
لم نزرع فائزًا أو أصوات لجنة أو توقيعات مزيفة؛ مراحل التقييم والقرار والنتيجة تمر عبر عمليات النظام الحقيقية.

مرفقات الـSeed صور PNG صغيرة صالحة ومسمّاة `DEMO-placeholder`، لتجربة التنزيل والتحقق من وجود ملف فقط.
ليست وثائق رسمية أو دليل مطابقة فعلي؛ ارفعي PDF/PNG/JPEG تجريبيًا واضحًا عند تجربة الرفع والمراجعة التفصيلية.

## السايكل الأساسية من البداية للنهاية

1. **Admin:** راجعي الحسابات والأدوار. جرّبي اعتماد `supplier-pending` بعد فتح مرفقه وتسجيل السبب. لإنجاز سيناريو رفض مستقل سجّلي موردًا جديدًا ولا تغيّري الموردين الأربعة الأساسيين.
2. **requester-it:** أنشئي طلبًا بعنوان جديد وأصناف وكميات ومبرر ثم أرسليه. تحققي من ظهوره عند officer ومن الإشعار.
3. **officer:** جرّبي Return مع سبب على طلب، ثم **requester-it** يعدّل ويعيد الإرسال؛ افحصي التاريخ والرسائل. جرّبي Reject على طلب مستقل، وAccept على طلب السايكل الرئيسي.
4. **officer:** أنشئي Tender من الطلب المقبول. استخدمي شاشة المتطلبات/Workflow المربوطة بالعطاء لتعيين manager + evaluator-department + evaluator-financial + evaluator-technical. يجب أن يكون ممثل القسم من قسم الطلب نفسه.
5. **officer:** أرسلي طلب الأوزان. كل واحد من الأعضاء الأربعة يرسل مقترحه من حسابه. **manager** يعتمد المتوسط؛ افحصي منع الفتح قبل الاعتماد ومنع المقترح المكرر. لا تفرضي 50/50؛ أدخلي مقترحات مجموع كل منها 100 حسب الحالة.
6. **officer:** افتحي التقديم بموعد مستقبلي، وجرّبي البحث والفلترة والتنقل بين الفئات. اختاري it1 وit2 وit3 وit4. تحققي أن المورد الموقوف أو المرفوض أو غير الفعّال لا يشارك، وأن الدعوة المكررة لنفس الجولة تُرفض من السيرفر.
7. **الموردون:** it1 وit2 وit3 يقبلون، وit4 يرفض أو يقدّم عرضًا رابعًا حسب التجربة. افحصي وصول الدعوة والإشعار وتفاصيل الشروط والكميات والموعد. القبول وحده يجب ألا يزيد عدد العروض المرسلة.
8. **الموردون الثلاثة:** أنشئي Draft، أدخلي أسعارًا مختلفة ومدة تسليم ومواصفات وتكاليف إضافية، ارفعي وثائق، احفظي وعدّلي ثم Submit. افحصي My Offers والتفاصيل والملخص الشخصي. بعد الإرسال لا تعدّلي نفس النسخة بحرية.
9. **officer:** أغلقي التقديم بعد الموعد، أو بعد أن يقدّم كل المدعوين عروضهم/يرفضوا؛ وجود دعوة Pending يمنع الإغلاق المبكر. راجعي العروض والمرفقات والمقارنة.
10. **officer:** سجّلي المطابقة. لا تعتبري عرضًا Compliant دون مرفقات أو مع نواقص. سجّلي سبب NonCompliant بوضوح. PendingClarification → رسالة للمورد → رد → مراجعة → حسم المطابقة. الرد لا يغيّرها تلقائيًا.
11. **officer:** اختاري Proceed بعد إغلاق الجولة، مع تحقيق شرط العدد. شغّلي تحليل AI ثم راجعيه من الموظف؛ لا تتجاوزي هذه الخطوة بتسجيل تحليل وهمي. جهّزي موعد لجنة التقييم بعد استكمال المطابقة.
12. **اللجنة:** جرّبي رابط الاجتماع، كل عضو يدخل درجاته وتوضيحاته ضمن وقت الجلسة؛ جرّبي المستخدم غير المعيّن، والدرجات الناقصة/خارج المدى، وتكرار الإرسال وانتهاء الوقت. افحصي المالي والفني والترتيب وفق الأوزان المعتمدة.
13. **اللجنة:** ولّدي التقرير وراجعي PDF ونسخته وتوقيعات الأعضاء الأربعة. افحصي رفض التوقيع دون التأكيد/المتطلبات. **officer** يراجع ويتابع ويحيل؛ لا يختار الفائز أو يقبل/يرفض تقييم اللجنة بدل صاحب القرار.
14. **manager:** جرّبي Approve في السايكل الرئيسية. لاختبار Return أو Reject كرري السايكل على عطاء مستقل؛ افحصي السبب والإشعار والنسخة الجديدة بعد الإرجاع وحفظ القديمة.
15. **الإحالة وTop Committee:** عيّني top1 إلى top4 في المرحلة المناسبة، ثم افتحي التقرير من كل حساب للتصويت والتوقيع. جرّبي سيناريو كلهم Approve وسيناريو فيه Reject على عطاء مختلف، حسب سياسة الاعتماد الفعلية في إعدادات المشروع.
16. **manager ثم officer:** استلمي القرار النهائي عبر المدير، acknowledgement ثم خطوات الإغلاق/الترسية المتاحة حسب القرار والسياسة. لا تتواصلي من حساب officer مباشرةً مع Top خارج مسار النظام.
17. **officer:** راجعي رسائل النتيجة وأرسلي Notify Suppliers مرة واحدة. **كل مورد مشارك** يفحص إشعاره ونتيجته فقط. أعيدي محاولة التبليغ للتحقق من منع التكرار. فرّقي بين تسليم إشعار داخلي ونجاح بريد خارجي.
18. **Admin والأدوار المصرّح لها:** راجعي Audit Logs والتقارير والفلترة والتصدير؛ قارني الأعداد بالعمليات التي نفذتها.

## حالات إضافية على عطاءات منفصلة

- صفر عروض، عرض واحد، عرضان، ثلاثة وأربعة: احسبي العروض Submitted لموردين مختلفين، لا الدعوات أو Drafts.
- أعيدي الطرح مع حفظ الجولات القديمة. اختبري مسار الاستثناء بعد ثلاث جولات فاشلة وقرار المدير؛ لا تفترضي أن عرضين يكفيان في الجولة الأولى.
- اختبري Pending/Accepted/Declined، قبول دون عرض، انتهاء الموعد، النقر مرتين، وطلب POST دون antiforgery token.
- جرّبي سعرًا سالبًا، كمية صفرية، صنفًا ناقصًا أو مكررًا، صنفًا من عطاء آخر، صلاحية عرض منتهية، وتكاليف إضافية سالبة.
- جرّبي ملفًا صحيحًا، امتدادًا غير مسموح، ملفًا فارغًا، أكبر من 10MB، ورابط تنزيل وثيقة مورد آخر.
- بعد التسجيل جرّبي OTP صحيحًا/خاطئًا/منتهيًا وإعادة الإرسال، انتظار الاعتماد، الموافقة والرفض، وتفعيل الحساب وكلمة المرور الأولى وإعادة تعيين كلمة المرور.
- جرّبي إيقاف مستخدم وتغيير دوره من Admin، ثم إعادة طلب الصفحة بجلسة سابقة للتحقق من فحص الصلاحيات.
- المورد لا يدخل Admin أو اللجنة ولا يفتح بيانات أو أسعار منافسيه بتغيير رقم الرابط، ولا يرسل رسالة مباشرة للمدير أو Top أو لجنة التقييم.
- الاختبارات المتعارضة تحتاج عطاءً جديدًا؛ العطاء المرفوض لا يتحول إلى السايكل الناجحة بإعادة Seed. لا تحذفي القاعدة لتجربة حالة جديدة.

## متطلبات الخدمات التي لا تنشئها الحسابات وحدها

- **OTP/البريد:** من مجلد مشروع الويب شغّلي `node Tools/DevMail/server.js` ثم افتحي `http://127.0.0.1:8025` في وضع Development/LocalInbox. عناوين `.test` ليست بريدًا حقيقيًا.
- **AI:** يحتاج Ollama وخادمًا ونموذجًا متاحين حسب إعدادات `Ollama`. إذا فشل الاتصال، هذه مشكلة إعداد خدمة وليست نقص حسابات؛ لا نعتبر السايكل ناجحة دونها.
- **الاجتماع:** إنشاء Zoom حقيقي يحتاج بياناته. النظام يدعم مسار Jitsi حسب الإعدادات. السماح بالكاميرا والمايك وتجربة الاجتماع يحتاج متصفحًا وأشخاصًا فعليين.
- **التوقيع وPDF:** يعتمد على إعداد ReportSigning والشهادة ووضع التطوير. عالجي رسالة إعداد الشهادة إذا ظهرت؛ لا نغيّر سياسة التوقيع أو الاعتماد لتجاوزها.
- **Face/Passkey:** سجّلي بياناتك بنفسك على حساب اختبار مخصص؛ لا يزرع الـSeed وجهًا أو بصمة. المورد الذي سجّل biometrics قد يُمنع من الدخول بكلمة المرور وحدها حسب السياسة الحالية.

## ما تحقّقنا منه بالفعل

نجح البناء دون تحذيرات أو أخطاء. أُضيف 33 حسابًا جديدًا إلى الحسابات الأربعة الموجودة؛ استُخدم الـOfficer الحالي دون تغيير كلمة مروره. جرى فحص كلمات مرور الحسابات الجديدة وأدوارها و67 تحققًا، منها فحوص HTTP عبر ASP.NET Core test host مع قاعدة SQL Server الحقيقية وكوكيز Identity وفحص احتفاظ الـOfficer بدوره.
يشمل تسجيل الدخول المسموح/الممنوع، dashboards، صفحات Supplier، عزل عرض ووثيقة شركة أخرى، تحرير Draft ومنع تحرير Submitted.
التفاصيل المحلية في `App_Data/SajaDemo/verification.txt`.

هذه ليست شهادة نجاح لكل الميزات أو اختبارًا كاملًا بالمتصفح. السايكل الكاملة والتكاملات والحالات أعلاه قائمة تجربة يدوية، وتُسجل نتائجها عند تنفيذها.
التحقق الآلي يفترض حالات التجهيز الأولية وكلمات المرور الأولى؛ بعد تغيير كلمات المرور أو إرسال المسودات لا تعيدي تشغيله باعتباره اختبارًا مطابقًا لنفس الحالة.

## ملاحظة من مراجعة الكود الحالي

اختيار الموردين وإرسال الدعوات في `TendersController`، وكذلك `TenderWorkflowService.Invite`، يفحص حالة الشركة Approved لكن لا يضيف فحص وجود حساب فعّال مرتبط بها في نفس الاستعلام.
لذلك قد يظهر `supplier-inactive` ضمن الاختيارات رغم أن دخوله ممنوع. هذا سيناريو يكشف نقصًا في التطبيق الحالي، وليس نجاحًا متوقعًا للاختبار.
تركنا كود الدعوات كما هو ضمن هذه المهمة التي تجهّز بيانات الاختبار؛ لا تعتبري وجود الحسابات دليلًا أن كل المتطلبات مطبّقة.
